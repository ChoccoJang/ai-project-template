# 0005. Phase는 머리말 필드로 적고, status는 표 하나로 유지하며, 규약은 CI가 검사한다

- 상태: Accepted
- 날짜: 2026-08-19
- Phase: 해당 없음
- 관련: `.ai/adr/0001-phase-naming.md`, `AGENTS.md` 13·14절, `.ai/status.md`

## 배경

세 가지가 같은 뿌리에서 나온 문제였다 — **기록이 서로를 가리키게 하는 장치가 규약뿐이고,
그 규약을 지켰는지 확인하는 수단이 없다.**

1. **Phase가 자유 텍스트다.** ADR 0001이 Phase 표기를 정하고 14절이 "특정 Phase에 속하는
   기록이면 본문에 `Phase A-1`로 밝힌다"고 했지만, 세 템플릿 머리말에 필드가 없었다.
   본문 어디에 어떤 형식으로 쓸지 정해지지 않으니 "A-2에 얽힌 결정·이슈·작업"을 모으는
   신뢰할 수 있는 방법이 없었다.
2. **`.ai/status.md`가 같은 사실을 두 표로 관리한다.** "Phase 구성"(시간축)과 "컴포넌트별
   구현 현황"(구조축)은 같은 데이터의 두 뷰다. 기능 하나가 끝나면 두 표를 다 고쳐야 하고,
   상태 어휘까지 갈려 있었다(`✅ 완료` vs `✅ 구현됨`).
3. **인덱스 등록이 검사되지 않는다.** `check_markdown_links.py`는 "인덱스가 가리키는 파일이
   있는가"만 본다. 반대 방향 — 파일을 만들고 인덱스에 등록하지 않은 경우 — 은 아무도 잡지
   못해, 규약이 에이전트의 성실성에만 의존했다.

검토했으나 채택하지 않은 대안:

- **status의 두 표 유지 + 갱신 규칙 명문화** — 규칙을 늘려도 갱신 지점이 둘이라는 사실은
  그대로다. 이 저장소가 이미 겪은 실패 방식이다.
- **인덱스 정합성 검사를 위한 새 워크플로 추가** — Actions 분을 더 쓴다(13절). 기존
  `docs-check.yml`에 step 하나를 더하는 편이 낫다.

## 결정

### 1. Phase는 머리말 필드로 적는다

- ADR·이슈·작업 결과 템플릿 머리말에 `Phase` 필드를 둔다.
- 값은 소분류 표기(`A-2`) 또는 Phase 표기(`A`), 속하지 않으면 **`해당 없음`**. 비워두지 않는다.
- 각 폴더의 인덱스 표에 `Phase` 열을 둔다.
- 효과: `grep -l "Phase.*A-2" .ai/*/*.md` 한 번으로 그 소분류의 전 이력이 모인다.
- 기존 ADR에도 필드를 소급 추가한다. 머리말 필드는 본문이 아니므로 "과거 ADR 본문은
  고쳐 쓰지 않는다"에 걸리지 않는다(`상태` 필드를 갱신하는 것과 같다).

### 2. `.ai/status.md`는 표 하나로 유지한다

- "Phase 구성"과 "컴포넌트별 구현 현황"을 **`구현 현황` 표 하나**로 합친다.
  열: `소분류 | 컴포넌트 · 기능 | 목표 | 상태 | 근거`.
- 소분류로 정렬하면 계획 뷰, 컴포넌트로 정렬하면 구조 뷰가 된다 — 갱신 지점은 한 줄 하나다.
- 상태 어휘를 `✅ 완료 · 🟡 진행 중 · 🚧 시작 전` 하나로 통일한다.
- `근거` 열(ADR/PR)을 필수로 둔다. 기존에 권고였던 "변화를 만든 링크를 남긴다"가 표의
  형태로 강제된다.
- "우선순위(다음에 할 일)" 절은 유지한다. 그것은 **순서**라는 다른 정보다.

### 3. 규약은 CI가 검사한다

- `.github/scripts/check_doc_index.py`를 추가하고 기존 `docs-check.yml`에 step으로 건다
  (새 워크플로를 만들지 않는다 — 13절).
- 검사 항목: 파일명 규칙(ADR 0003) · 번호 중복 · 인덱스 등록 여부 · `Phase` 필드 존재와
  형식 · `상태` 어휘 · **파일 머리말 상태와 인덱스 표 상태의 일치**.
- 상태 비교는 첫 쉼표·괄호 앞까지를 기준으로 한다(`Resolved (2026-08-19, PR #12)` ↔
  `Resolved`를 같게 본다).

## 결과

- 기록 세 종류가 `Phase` 하나로 교차 검색된다. ADR 0001이 정한 표기가 비로소 쓰임새를 갖는다.
- status 갱신 누락이 구조적으로 줄어든다 — 고칠 줄이 하나뿐이다.
- 1·2번 규칙과 ADR 0003의 파일명 규칙이 문서에만 있는 약속이 아니라 CI가 막는 조건이 된다.
- 트레이드오프: 컴포넌트가 많아지면 status의 단일 표가 길어진다. 그때는 요약표를 되살리지
  말고 소분류별 소제목으로 표를 나눈다(갱신 지점은 여전히 하나).
- 트레이드오프: 문서 검사 step이 하나 늘어 PR마다 몇 초를 더 쓴다. 표준 라이브러리만 쓰고
  설치 단계가 없어 분 소모는 무시할 수준이다.
