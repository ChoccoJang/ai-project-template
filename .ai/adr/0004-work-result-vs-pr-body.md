# 0004. 작업 결과 문서와 PR 본문은 역할을 나누고, 같은 내용을 두 번 쓰지 않는다

- 상태: Accepted
- 날짜: 2026-08-19
- Phase: 해당 없음
- 관련: `AGENTS.md` 9절, `.github/pull_request_template.md`

## 배경

규칙이 같은 글을 두 번 쓰게 만들고 있었다.

- `AGENTS.md` 9절: "PR을 생성할 때는 `pull_request_template.md`를 본문으로 채운다."
- 같은 9절: "작업 결과 문서의 본문(작업내용)은 `pull_request_template.md`의 각 섹션을
  채워서 작성한다."

그래서 목적·변경 내용·검증·관련·체크리스트가 PR과 작업 결과 문서 양쪽에 그대로 들어갔다.
비용은 작성 노력만이 아니다 — 리뷰 중에 PR 본문이 갱신되면 이미 쓴 작업 결과 문서가 조용히
낡는다.

특히 **체크리스트가 문제였다.** 체크리스트는 머지 전에 통과 여부를 확인하는 **게이트**다.
머지된 뒤 기록 문서에 남은 `- [ ]`는 아무것도 막지 못하고, 실제로 미체크 상태 그대로 남은
항목들이 있었다. 기록이 아니라 잔여물이다.

검토했으나 채택하지 않은 대안:

- **PR 본문을 먼저 쓰고 머지 후 그대로 복사한다** — 두 번 *작성*하지는 않지만 사본이 남아
  결국 한쪽이 낡는다. 낡는 방향이 예측 가능해질 뿐 중복 자체는 그대로다.
- **작업 결과 문서를 없애고 PR만 남긴다** — 작업요청사항(소유자가 무엇을 요청했는가)과
  제안사항은 PR 본문에 들어갈 자리가 없다. 저장소 안에 남길 이유가 있는 정보다.

## 결정

### 1. 섹션별 소유자를 하나로 정한다

| 내용 | PR 본문 | 작업 결과 문서 |
|---|---|---|
| 목적 / 배경 | ✅ | ❌ (PR 링크로 대신한다) |
| 변경 내용 | ✅ 리뷰용 상세 | ✅ **파일·모듈별 한 줄 요약** |
| 검증 | ✅ | ❌ |
| 체크리스트 | ✅ (머지 전 게이트) | ❌ |
| 작업요청사항 | ❌ | ✅ |
| 최종정리내용 · 참고사항 · 제안사항 | ❌ | ✅ |

### 2. 상호 참조를 필수로 만든다

- 작업 결과 문서 머리말에 **`PR` 필드**를 둔다. PR 없이 직접 push했다면 `없음(직접 push)`과
  그 사유를 적는다.
- PR이 없는 작업이면 변경 내용에 근거까지 적는다 — 그때는 이 문서가 유일한 기록이다.

### 3. 체크리스트는 PR에만 둔다

- 작업 결과 문서 템플릿에서 `검증`·`체크리스트` 절을 삭제한다.

## 결과

- 작업 결과 문서가 절반 이하로 줄고, 각 사실이 저장소 안에 한 번만 존재한다.
- 트레이드오프: 배경과 검증 내역을 보려면 PR을 열어야 한다. 저장소만으로 이력을 완결하려던
  성질을 일부 포기하는 대신, 두 사본이 어긋날 가능성을 없앤다. PR이 없는 작업은 예외로
  두어 최소한의 자기완결성은 남긴다.

## 영향 파일

- `.ai/work-result/0000-template.md`: 검증·체크리스트 절 삭제, `PR` 필드 추가, 작업내용 →
  변경 내용(요약)으로 축소.
- `.ai/work-result/README.md`: PR 템플릿을 채워 쓰라는 안내 삭제, 역할 분리 문구로 교체.
- `AGENTS.md` 9절 "작업 결과 문서": 같은 취지로 개정.
- `.ai/README.md` "작업 결과 문서 남기는 법": 같은 취지로 개정.
