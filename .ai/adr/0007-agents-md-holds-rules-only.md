# 0007. `AGENTS.md`는 규칙만 담는다 — 범위·계약·프로젝트 소개는 각자의 문서로

- 상태: Accepted
- 날짜: 2026-08-19
- Phase: 해당 없음
- 관련: `.ai/adr/0006-backlog-and-living-design-docs.md`, `.ai/adr/0005-phase-field-and-single-status-table.md`, `AGENTS.md`

## 배경

ADR 0006은 "하고 싶은 것"을 규칙 문서에서 떼어내 `.ai/backlog.md`로 옮겼다. 근거는 **갱신
주기가 다른 것을 한 파일에 두면 규칙 문서가 계속 흔들린다**는 것이었다.

그런데 그 근거를 끝까지 적용하지 않았다. "하고 싶다"는 뺐는데 **"하기로 했다"(2절 Scope의
범위 목록)는 규칙 문서에 그대로 남겼다.** 범위는 결정할 때마다 바뀌고 규칙은 드물게 바뀌므로,
같은 문제가 그대로 남는다.

게다가 범위 목록은 `.ai/status.md`의 구현 현황 표와 **같은 것을 두 번 적는다.** "무엇을
만들기로 했나"(2절)와 "그것이 어디까지 됐나"(status 표)는 같은 항목의 두 얼굴이다. ADR 0005가
status 안의 두 표를 하나로 합친 것과 정확히 같은 문제다.

훑어보니 2절만이 아니었다. `AGENTS.md`에 규칙이 아닌 것이 더 있었다.

- **머리말** — `{{프로젝트명}}은 …이다` 프로젝트 소개.
- **1절 Mission** — "{{프로젝트명}}을 구현한다", "{{핵심 데이터 흐름}}을 유지한다" 같은
  프로젝트 목표. 같은 절에 "과도한 추상화보다 최소 기능을 우선한다"는 **규칙**이 섞여 있었다.
- **7절 Interface Contract** — 계약의 **내용**을 어디에 둘지 정하면서 그 자리를 프로젝트에
  맡겨 두었다. 계약 내용은 설계이지 규칙이 아니다. ADR 0006이 `.ai/design/`을 만든 뒤로는
  갈 곳이 정해졌다.

검토했으나 채택하지 않은 대안:

- **범위를 `.ai/backlog.md`의 한 구획으로 둔다** — 백로그는 "아직 아닌 것"의 자리다. 확정된
  범위가 섞이면 두 성격이 다시 한 파일에 들어간다.
- **범위를 담을 문서를 새로 만든다(`.ai/scope.md`)** — status의 구현 현황 표와 항목이
  일대일로 겹친다. 갱신 지점이 둘로 늘 뿐이다.

## 결정

### 1. 모든 절은 규범이어야 한다

`AGENTS.md`의 각 절은 **"무엇을 지켜라"** 를 말한다. 사실(현재 무엇이 있나)·계획(무엇을
만들 건가)·설계(어떻게 생겼나)는 담지 않고, 그것을 담는 문서를 가리킨다.

### 2. 범위의 단일 출처는 `.ai/status.md` 구현 현황 표

- 2절은 **범위 규칙**만 남긴다 — 그 표에 없는 것은 하지 않는다, 새로 넣는 것은 소유자가
  정한다, 미리 구현하지 않는다.
- 아이디어가 범위가 되는 흐름은 문서 하나 안에서 이어진다.

  ```text
  .ai/backlog.md   →   .ai/status.md 구현 현황 표   →   .ai/status.md 우선순위
    하고 싶다             하기로 했다 (🚧 시작 전)          다음에 한다        →  ✅ 완료
  ```

### 3. 프로젝트 소개·목표는 `README.md`

- 머리말과 1절에서 프로젝트 서술을 걷어낸다. 1절은 **에이전트가 따르는 작업 원칙**만 남긴다.

### 4. 인터페이스 계약 내용은 `.ai/design/`

- 7절은 **계약을 다루는 규칙**만 남긴다 — 계약은 설계 문서에 두고, 제공 측이 문서화하며,
  바꿀 때 문서와 코드를 함께 고치고 근거는 ADR로 남긴다.

### 5. 예외 — 값 자체가 규칙인 것은 남긴다

4절의 저장소 배치와 5절의 빌드/실행 표는 값이 들어 있지만 `AGENTS.md`에 남긴다. **"어디에
두는가"와 "무엇으로 빌드하는가"는 값이 곧 규칙**이고, 규칙과 값이 갈리면 오히려 찾기 어려워진다.
에이전트가 가장 먼저 찾는 정보이기도 하다.

기준: **값을 바꾸는 것이 곧 규칙을 바꾸는 것이면 남기고, 값만 바뀌는 것이면 옮긴다.**

## 결과

- 규칙 문서를 여는 빈도가 줄어든다. 범위를 늘리거나 계약을 고칠 때 `AGENTS.md`를 건드리지
  않는다 — 규칙이 흔들리지 않는다.
- "무엇을 만들기로 했나"와 "어디까지 됐나"가 한 표에서 읽힌다. 두 곳에 적을 일이 없다.
- ADR 0006의 "채택되면 `AGENTS.md` 2절 범위로 올린다"는 이 결정으로 대체된다. 0006의 핵심
  (백로그·설계 축 신설)은 그대로 유효하므로 `Superseded` 처리하지 않는다.
- 트레이드오프: `AGENTS.md`만 읽어서는 이 프로젝트가 무엇을 만드는지 알 수 없다. 머리말이
  `README.md`와 `.ai/status.md`를 가리키므로 한 단계 더 이동해야 한다. 규칙 문서가 규칙만
  담는 대가로 받아들인다.

## 영향 파일

- `AGENTS.md`: 머리말·1절·2절·7절을 규범으로 다시 씀. 4·5절은 예외로 유지하되 그 이유를 명시.
- `.ai/status.md`: 구현 현황 표가 범위의 단일 출처임을 명시.
- `.ai/backlog.md`: 흐름 도식에서 `AGENTS.md` 2절 경유를 제거.
- `.ai/design/README.md`: 인터페이스 계약도 이 폴더가 담는다고 명시.
- `README.md`: 설계 의도의 해당 항목 갱신.
