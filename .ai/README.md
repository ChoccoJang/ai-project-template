# .ai — AI 에이전트 공용 작업 메모리

이 폴더는 이 저장소에서 일하는 **AI 에이전트(Claude Code, Codex)** 가 공유하는 개발 과정의
기록이다. 특정 도구에 종속되지 않으며, 배포물이 아니라 저장소에서만 보는 내부 문서다.

> 규칙은 [`AGENTS.md`](../AGENTS.md)가 단일 출처다. 이 파일은 **`.ai/` 문서들의 역할과 추가
> 절차**를 정한다.

## 문서별 역할

문서를 나누는 축은 주제가 아니라 **어떻게 갱신되는가**다. 덮어쓰는 문서와 추가만 하는 문서를
한 파일에 섞으면 둘 다 망가진다 — 최신 상태를 보려면 과거를 걷어내야 하고, 과거를 보려면
이미 덮어쓴 뒤다.

| 질문 | 문서 | 갱신 |
|---|---|---|
| 만들고 싶은 게 뭔가 | [`backlog.md`](./backlog.md) | 덮어씀 |
| 무엇을 만들기로 했고 어디까지 됐나 | [`status.md`](./status.md) | 덮어씀 |
| 지금 어떤 모습인가 | [`design/`](./design/) | 덮어씀 |
| 왜 그렇게 정했나 | [`adr/`](./adr/) | **추가만** |
| 왜 아직 안 됐나 | [`issues/`](./issues/) | 상태 갱신 · 사실 보강 |
| 무엇을 했나 | [`work-result/`](./work-result/) | **추가만** |

- **[`backlog.md`](./backlog.md)** — 하고 싶지만 아직 범위가 아닌 것. 채택되면 `status.md`의
  구현 현황 표에 `🚧 Not started`로 옮기고 여기서 지운다. 채택은 소유자가 정한다.
- **[`status.md`](./status.md)** — 구현 현황. **이 문서의 구현 현황 표가 곧 범위다.**
  다른 문서는 상태를 자체 서술하지 않고 이 문서를 인용한다.
- **[`design/`](./design/)** — 지금의 설계와 인터페이스 계약. 컴포넌트 1개 = 파일 1개.
  현재 모습만 담고 덮어쓴다. "왜"는 담지 않고 ADR을 링크한다. **미리 만들지 않고**,
  컴포넌트가 실제로 생겨 구조를 설명해야 할 때 만든다.
- **[`adr/`](./adr/)** — 결정 1건 = 파일 1개. 배경·결정·결과를 남긴다.
- **[`issues/`](./issues/)** — 미해결이거나 의도적으로 미룬 것. **이미 정해졌거나 이미 있는
  것**의 문제를 담는다 — 아직 할지 정하지 않은 아이디어는 `backlog.md`다(그 문서의 판단 표).
  같은 문제의 사례를 새로 발견하면 **본문에 덧붙인다.** 상태만 고칠 수 있는 문서가 아니다 —
  본문을 고치지 못하는 것은 `adr/`뿐이다.
- **[`work-result/`](./work-result/)** — 작업 1건 = 파일 1개. PR 본문과 중복해서 쓰지 않는다
  (역할 분담은 `AGENTS.md` 8절).

그 밖의 문서가 필요해지면 이 폴더 아래에 두고 이 목록에 등록한다. 미리 만들어 두지 않는다.

## 처음 채울 때 — 최소 집합

문서 세트를 도입한 첫 작업에서 **전부 만들 필요는 없다.** 다음 셋이면 에이전트가 일할 수 있다.

| 필수 | 왜 |
|---|---|
| `AGENTS.md`의 📝 절 | 규칙이 비면 그다음이 전부 막힌다 |
| [`status.md`](./status.md) | 범위의 단일 출처. 여기 없는 것은 하지 않는다 |
| 프로젝트 `README.md` | 이 프로젝트가 무엇인지 |

`adr/`·`design/`·`issues/`·`work-result/`는 **그것을 남길 일이 실제로 생겼을 때** 만든다.
빈 인덱스로 두는 것이 정상이다. 첫날부터 문서가 코드보다 많아지면 절차를 잘못 읽은 것이다.

## 새 문서 추가하기

1. 해당 폴더의 `0000-template.md`를 복사해 파일을 만든다.

   | 폴더 | 파일명 |
   |---|---|
   | `adr/`, `issues/` | `NNNN-slug.md` (마지막 번호 +1, 4자리 zero-pad) |
   | `work-result/` | `yyyymmdd-slug.md` |
   | `design/` | `{{component}}.md` |

   슬러그는 **영문 소문자·숫자·하이픈**만 쓴다(`AGENTS.md` 7절). 한글 제목은 파일 안의 H1과
   인덱스 표의 링크 텍스트가 담는다.

2. 머리말을 채운다. ADR·이슈·작업 결과는 `Phase` 필드를 비워두지 않는다(없으면 `해당 없음`).
3. **그 폴더의 `README.md` 인덱스 표에 한 줄 추가한다.** 템플릿 파일은 인덱스에 넣지 않는다.
4. 그 폴더의 **첫 문서라면** 인덱스의 `(없음)` 행과 "아직 등록된 …이 없다" 문장, 그 아래
   **기입 예시 블록을 지운다.** 실제 행이 생긴 뒤에도 남겨 두면 사실과 어긋난다.
5. **템플릿의 안내용 HTML 주석(`<!-- ... -->`)은 값을 채우고 지운다.** 완성된 문서에 안내가
   남아 있지 않게 한다.

빠뜨린 것은 CI가 잡는다. 올리기 전에 로컬에서 먼저 돌린다.

```bash
python3 .github/scripts/check_markdown_links.py
python3 .github/scripts/check_doc_index.py
```

## 머리말 필드

문서마다 머리말에 넣을 항목이 다르다. **CI 강제** 표시가 붙은 것은 비어 있거나 형식이
어긋나면 `check_doc_index.py`가 잡는다 — 나머지는 템플릿이 요구하는 항목이니 함께 채운다.

| 문서 | 항목 |
|---|---|
| `adr/` | `상태` **(CI 강제)** · `Phase` **(CI 강제)** · `날짜` · `관련` |
| `issues/` | `상태` **(CI 강제)** · `Phase` **(CI 강제)** · `관련` |
| `work-result/` | `PR` **(CI 강제)** · `Phase` **(CI 강제)** · `작업일시` · `작업자` |
| `design/` | `갱신일` **(CI 강제)** · `관련 ADR` |
| `backlog.md` · `status.md` | 머리말 없음 |

- `Phase` 값은 `A` 또는 `A-1`, 속하는 Phase가 없으면 `해당 없음`(아래 Phase 표기).
- `관련`·`관련 ADR`처럼 채울 것이 없는 항목은 **비우지 말고 `해당 없음`** 으로 적는다.
  설계 문서가 ADR보다 먼저 생기는 것은 정상이다 — 그때 `관련 ADR`은 `해당 없음`이다.
- 이 표에 없는 항목을 임의로 추가하지 않는다. 필요하면 템플릿부터 고친다.

## 문서가 커질 때

- **인덱스 표는 자라는 것이 정상이다.** 상한을 두지 않는다. 다만 **50줄을 넘으면 상태별로
  절을 나눈다**(예: `Accepted` / 지난 것). 표를 자르지는 않는다 — grep으로 찾기 때문이다.
- **개별 기록이 300줄을 넘으면** 한 파일에 여러 건이 섞인 것이다. ADR은 결정 1건, 이슈는
  문제 1건이 원칙이므로 나눈다.
- **`status.md`의 끝난 Phase는 한 줄로 접는다.** 세부는 `work-result/`가 갖고 있다.
- 진입 문서(`AGENTS.md` · `CLAUDE.md` · 이 파일 · `status.md`)는 합계 예산을 지킨다
  (`AGENTS.md` 7절).

## Phase 표기

작업을 여러 단계로 나눌 때 쓰는 표기다. 지금 어느 Phase인지는 [`status.md`](./status.md)가
단일 출처이고, 여기서는 **표기 규칙**만 정한다.

| 구분 | 형식 | 예 |
|---|---|---|
| Phase (대분류) | 대문자 알파벳 한 글자 | `Phase A`, `Phase B` |
| 소분류 | `대문자-숫자` | `A-1`, `A-2`, `B-1` |

- Phase는 `A`부터 순서대로 붙인다. 소분류 번호는 각 Phase 안에서 `1`부터 센다.
- **분리는 소분류까지만 한다.** `A-1-1` 같은 3단계 표기를 쓰지 않는다. 소분류 하나가 너무
  크면 다음 소분류로 쪼개거나 본문의 체크리스트·항목으로 푼다.
- **한 번 부여한 문자와 번호는 재사용하지 않는다.** 항목이 없어져도 재번호하지 않고 다음
  번호로 이어 붙인다. 단 **아직 다른 문서·커밋·브랜치가 참조하지 않은 번호는 정리해도 된다.**
- **첫 Phase는 `A` 하나로 시작한다.** `B`를 여는 것은 범위 결정이므로 소유자가 정한다
  (`AGENTS.md` 2절).
- 쓰는 곳: `status.md`의 현재 Phase·구현 현황 표·우선순위, 기록 문서의 `Phase` 머리말 필드,
  브랜치명(영문 소문자이므로 `a-1`로 쓴다).

## 상태 어휘

상태 값은 **아래 표에 있는 것만 쓴다.** 새 값을 만들지 않는다 — 표현하고 싶은 상태가 없으면
그 자체가 결정이므로 ADR로 남기고 이 표를 고친다.

- **값은 영어로 고정한다.** 문서 본문은 한국어지만(`AGENTS.md` 7절), 상태는 정해진 값 중
  하나를 고르는 것이라 번역하지 않는다. 한글로 쓰면 표기가 갈리고 검사가 불가능해진다.
- **부연은 값 뒤에 괄호로 붙인다.** 괄호 안은 자유 문구이고 한국어로 써도 된다
  (예: `Deferred (환경 제약)`). 검사와 비교는 괄호 앞의 값만 본다.
- 인덱스 표의 상태는 파일 머리말의 상태와 같아야 하며, CI가 확인한다.

### `adr/` — 결정의 상태

| 값 | 뜻 | 언제 |
|---|---|---|
| `Accepted` | 확정되어 적용됨 | 기본값. 결정을 내렸고 지금 유효하다 |
| `Proposed` | 제안됨, 미확정 | 소유자 승인을 기다린다 |
| `Superseded by NNNN` | 후속 결정으로 대체됨 | 뒤집혔다. 새 ADR 번호를 함께 적는다 |
| `Deprecated` | 더 이상 유효하지 않음 | 대체 결정 없이 폐기됐다 |

### `issues/` — 이슈의 상태

| 값 | 뜻 | 언제 |
|---|---|---|
| `Open` | 미해결 | 기본값 |
| `Deferred` | 의도적으로 미룸 | 사유를 괄호로 붙인다. 예: `Deferred (환경 제약)` |
| `Resolved` | 해결됨 | 날짜와 관련 PR/ADR을 괄호로 붙인다. 예: `Resolved (2026-07-31, PR #12)` |

### `status.md` — 항목의 진행

| 값 | 뜻 |
|---|---|
| `🚧 Not started` | 범위에 넣기로 했으나 아직 손대지 않았다 |
| `🟡 In progress` | 일부 되어 있고 TODO가 남았다 |
| `✅ Done` | 끝났다 |

`design/`과 `work-result/`에는 상태가 없다 — 설계는 항상 현재 모습이고, 작업 결과는 끝난
기록이다.

## 결정을 뒤집을 때

새 ADR을 쓰고, 옛 ADR의 상태를 `Superseded by NNNN`으로 바꾼 뒤 새 ADR에서 링크한다.
**과거 ADR의 본문은 고쳐 쓰지 않는다** — 그 시점의 판단으로 보존한다. 머리말 필드(`상태`,
`Phase`)와 파일명은 본문이 아니므로 규약이 바뀌면 맞춰 고친다.
