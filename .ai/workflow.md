# 작업 절차와 PR 운영

**커밋·PR·리뷰·추적 작업을 하기 전에 읽는다.** 공통 원칙은 [AGENTS.md](../AGENTS.md),
문서 작성법은 [README.md](./README.md)가 정한다. 아래 8·10절은 AGENTS.md의 같은 절이
위임한 상세 절차이며, 기존 단계 번호를 유지한다. 읽기만 하는 작업은 PR 절차가 해당 없다.

## 8. 커밋 / 브랜치 / PR 규칙

### 브랜치명 / PR 제목

```text
feature/yyyymmdd-work-name
```

- `yyyymmdd`는 브랜치를 만든 날짜, `work-name`은 **영문 소문자**에 하이픈이다.
  한글·공백·대문자를 쓰지 않는다.
- PR 제목은 브랜치명과 같은 값을 쓴다.
- **도구·세션이 이미 만든 브랜치는 그대로 쓴다.** 규칙에 맞추려고 새 브랜치를 만들지
  않는다 — 재명명하면 같은 작업에 브랜치가 둘 생긴다. 위 형식은 **에이전트가 브랜치를
  직접 만들 때** 적용한다.

### 커밋 메시지

```text
type(scope): 요약
```

- `type`과 `scope`는 영문, 요약과 본문은 문서 언어로 쓴다(AGENTS.md 7절).
- 쓸 수 있는 type: `docs` · `feat` · `fix` · `refactor` · `test` · `chore` · `infra`
- `scope`는 바뀐 대상을 가리키는 짧은 영문 낱말이다(모듈·폴더·문서 이름).

### PR

- **브랜치로 작업한 변경은 PR로 올리고, 리뷰를 받은 뒤 머지한다.** 리뷰 없이 기본
  브랜치에 바로 머지하지 않는다. 리뷰는 둘 중 하나다.
  - **상호 리뷰** — 사람이나 다른 에이전트가 본다. 가능하면 이쪽이다.
  - **자체 리뷰** — 볼 사람이 없을 때. 자기 diff를 처음 보는 사람처럼 다시 읽고, **무엇을
    확인했는지** PR 본문에 남긴다. "확인함"이 아니라 확인한 항목을 적는다.
- **원격이 없거나 저장소에서 PR 기능을 껐거나 소유자가 PR을 쓰지 않기로 했으면 이 항목은 "해당 없음"이다.** 기본
  브랜치에 직접 커밋하고 작업 결과 문서의 `PR` 필드에 사유를 적는다. **PR을 열 수 없다고
  작업을 멈추거나 머지되지 못할 브랜치를 만들지 않는다.**
- **본문은 [`.github/pull_request_template.md`](../.github/pull_request_template.md)를 채워
  쓴다.** API·CLI로 만들 때는 그 파일을 직접 읽어 채운다. 빈 섹션을 두지 않고, 해당 없으면
  "해당 없음"으로 적는다. 안내용 HTML 주석은 지운다.
- **PR을 연 뒤에는 CI·리뷰 반응을 계속 추적하고, 끝나면 뒷정리까지 한다.** 언제 무엇을
  하는지는 10절이, 추적에 쓸 수단은 도구별 파일이 정한다.

### 코멘트 이모지 신호 (머지 / 중단)

소유자가 매번 채팅으로 확인해 주지 않아도 되도록, **소유자가 PR 코멘트로 낸 이모지를 지시로
본다.**

| 신호 | 뜻 | 조치 |
|---|---|---|
| 🚀 | 머지해도 된다 | CI green·리뷰 지적 해소를 함께 확인하고 머지한다 |
| 👎 · ❌ · 🛑 | 머지하지 않는다 | PR을 close한다. 남은 지적은 `.ai/issues/`에 등재한다 |

- **코멘트에서만 읽는다.** 소유자가 쓴 **코멘트 본문의 이모지**와 **코멘트에 달린 반응**,
  이 둘뿐이다.
- **자리마다 쓸 수 있는 기호가 다르다.** 반응으로 달 수 있는 이모지는 여덟 개뿐이라
  **반응 자리에서는 🚀·👎만** 인정하고, **코멘트 본문에서는 ❌·🛑도 중단 신호**로 읽는다.
- **어느 자리든 낸 사람이 소유자**여야 한다.
- **코멘트에 다른 말이 함께 있으면 그 말이 우선한다.** 지적·질문이 섞인 코멘트의 🚀는 승인이
  아니라 "이건 하고 머지하라"는 뜻이고, 사유가 붙은 👎는 그 사유를 먼저 읽는다.
- **그 밖의 이모지는 신호가 아니다.** 실수로 누른 반응이 머지나 close를 일으키지 않게 한다.
- **승인자는 `project-rules.md` 8절의 계정 목록으로 확인한다.** 목록이 미설정이거나 작성자를
  식별할 수 없는 반응은 승인·중단으로 처리하지 않는다. 확인 가능한 명시적 지시를 받는다.
- **소유자가 지정한 위임 승인 경로도 승인으로 본다.** 같은 절의 「위임 승인 경로」에 적힌
  경로(예: 소유자가 대화에서 지정한 PM 세션의 명시적 승인)만 해당하고, 적힌 범위를 넘지 않는다.
  이 경로의 승인도 대상 PR과 head SHA를 밝혀야 하며, 아래 SHA 규칙을 똑같이 따른다. 신호 URL
  대신 승인 메시지의 출처와 시각을 PR 본문에 남긴다.
- **머지 승인은 PR의 head SHA에 연결한다.** 승인자·신호 URL/ID·대상 head SHA를 PR 본문에
  기록한다. 대상 SHA를 확인할 수 없는 과거 반응은 승인으로 추정하지 않는다. 승인 후 head가
  바뀌면 다시 승인을 확인한다. 중단 신호는 해당 PR에 대한 최신 명시적 지시인지 확인한다.
- **머지 직전에 head SHA와 필수 검사를 다시 조회한다.** 최신 head 또는 GitHub가 요구하는
  test-merge 커밋의 필수 검사, 미해결 리뷰, 충돌, 저장소 보호 규칙을 확인한다. 머지 API에도
  확인한 head SHA를 조건으로 전달한다. SHA 조건을 지원하지 않으면 보호 규칙이 적용되는
  머지 수단을 사용하고, 동일 변경임을 보장할 수 없으면 머지하지 않는다.
- **신호가 없으면 머지도 close도 하지 않는다.** 되돌리기 어렵거나 논쟁 여지가 있는 변경은
  🚀가 있어도 한 번 더 묻는다.
- **어느 신호든 확인한 그 턴 안에서 종료 절차까지 끝낸다**(10절).

### 코드 리뷰

- **코드를 바꾼 작업은 PR을 열기 전에 코드 리뷰를 한 번 돌리고, 지적을 반영한 상태로 연다.**
  리뷰를 PR 뒤로 미루지 않는다 — 열자마자 고칠 것이 나오면 리뷰어의 시간을 두 번 쓴다.
  문서 전용 작업은 해당 없다.
  - 도구에 **코드 리뷰 기능이 있으면 그것으로 돌린다.** 무엇을 쓰는지는 도구별 파일이 정한다.
  - 없으면 위 **자체 리뷰**로 대신한다. 어느 쪽이든 **무엇을 봤는지** PR 본문에 남긴다.
- **변경이 없는 동일 diff의 반복 리뷰는 하지 않는다.** 수정한 부분과 영향 범위는 다시
  확인한다. 새로운 실패나 중요한 변경이 있으면 필요한 리뷰·검증을 추가한다. 해결한 지적과
  재검증한 범위를 PR 본문에 남기며, 추가 작업 범위가 필요한 지적만 소유자에게 확인한다.
- **리뷰에서 나왔지만 이번에 해결하지 못한 지적은 [`.ai/issues/`](./issues/)에 등재한다.**
  지적 1건 = 이슈 1건이고, 미루기로 한 것은 `Deferred`, 남은 것은 `Open`이다. PR 본문과 작업
  결과 문서에서 그 이슈를 가리킨다. **머지된다고 지적이 사라지는 것이 아니다** — 다음 작업은
  `.ai/issues/`를 먼저 읽고 시작하되, 그중 무엇을 실제로 할지는 범위가 정한다(AGENTS.md 2절).

### 브랜치 정리

- **지우는 대상은 이번 작업에 쓴 브랜치뿐이다.** 도구·세션이 만들어 준 브랜치도 여기
  해당한다(8절의 브랜치명). 그 밖의 브랜치는 머지되었더라도 손대지 않는다.
- **머지된 뒤에는 로컬·원격 브랜치를 모두 에이전트가 지운다.** 뒷정리를 소유자에게 넘기지
  않는다 — 종료 절차의 일부다(10절).
- **close된 뒤에는 원격에 모든 작업 커밋이 보존된 것을 확인하고 로컬만 지운다.** 원격은 남긴다.
  로컬에만 있는 커밋이나 미커밋 변경이 있으면 보존하고 알린다.
  close는 대개 "다시 하라"는 뜻이기 때문이다(👎). 남긴 브랜치 이름을 알리고 처분은
  소유자가 정한다.
- **권한이 없어 원격 브랜치를 지우지 못하면 그 사실만 알린다.** 지우지 못한 브랜치 이름을
  적어 소유자가 처리할 수 있게 한다. 조용히 넘어가지 않고, 우회 수단을 찾지도 않는다.
- **남이 만든 브랜치의 히스토리를 재작성하지 않는다.** rebase·amend·force push로 이미 올라간
  커밋을 지우지 않는다. 자기가 만든 브랜치에서도 남이 그 브랜치를 받아 갔다면 마찬가지다.

### 작업 결과 문서

- 작업이 끝나면 [`.ai/work-result/`](./work-result/)에 결과를 남긴다.
- **PR 본문과 같은 내용을 두 번 쓰지 않는다.** 섹션별 소유자는 다음과 같다.

  | 내용 | PR 본문 | 작업 결과 문서 |
  |---|---|---|
  | 목적 / 배경 | ✅ | ❌ (머리말 `PR` 필드로 가리킨다) |
  | 변경 내용 | ✅ 리뷰용 상세 | ✅ 파일·모듈별 한 줄 요약 |
  | 검증 · 체크리스트 | ✅ (머지 전 게이트) | ❌ |
  | 작업요청사항 | ❌ | ✅ |
  | 최종정리내용 · 참고사항 · 제안사항 | ❌ | ✅ |

- **PR이 없으면 위 표에서 ❌인 것도 작업 결과 문서가 담는다** — 그때는 이 문서가 유일한
  기록이다.
- **이 문서는 PR을 연 뒤에 만든다.** 작업한 변경만으로 PR을 먼저 열고, 받은 링크를 머리말
  `PR` 필드에 채운 채로 문서를 만들어 같은 브랜치에 커밋한다 — 링크는 번호가 아니라 링크로
  적고, `미정` 같은 임시값을 거쳐 가지 않는다(순서는
  [`.ai/work-result/README.md`](./work-result/README.md)).
- PR을 열지 않기로 한 작업이면 그 자리에 사유를 적는다 — `없음(직접 push)` ·
  `없음(커밋 없음)` · `없음(원격 저장소 없음)`처럼 **무엇 때문인지 드러나게** 쓴다. 이때는 변경 내용에 근거까지 남긴다 — 이 문서가 유일한 기록이다.
- **파일을 하나라도 바꿨으면 남기고, 읽기만 한 작업은 남기지 않는다.**

### 릴리즈 노트

- **[`.github/release-template.md`](../.github/release-template.md)를 채워 쓴다.** 양식과
  쓰는 규칙은 그 파일이 정한다. 빈 절을 두지 않고, 해당 없으면 지운다.
- **버전 번호와 배포 시점은 소유자가 정한다.**

## 10. 작업 절차 (체크리스트)

AGENTS.md 9절이 **무엇이 되어야 끝인가**를 정한다면, 이 절은 **어떤 순서로 하는가**를 정한다. 절차가
산문에 흩어져 있으면 도구마다 빠뜨리는 단계가 달라지므로 여기 한 줄씩 모아 둔다. **순서와
항목은 도구와 무관하게 같고, 수단(코드 리뷰 기능·구독·예약 같은 도구 기능)만 도구별 파일이
정한다.**

**작업을 끝내는 마지막 응답에 아래 블록을 그대로 옮겨 적고 각 항목의 결과를 채운다.**
**한 항목이 한 줄이다** — `/`로 이어 붙여 한 줄로 만들지 않는다. 항목을 지우거나 줄이지
않는다 — 해당 없으면 `해당 없음`과 사유를 적는다. 스스로 답을 적게 하는 것이 절차가 조용히
빠지는 것을 막는 유일한 장치다.

```text
[작업 절차]
- 시작일시:
- 종료일시:
- 걸린시간:
- 시작확인:
- 리뷰:
- 검사:
- 작업결과+PR링크:
- 추적 걸기:
- 뒷정리:
```

**일시는 KST로 적고, 반드시 명령으로 얻는다.** 모델은 현재 시각을 모르고, 원격 환경은
대개 UTC라 짐작하거나 환경의 기본 시간대를 그대로 쓰면 어긋난다. 아래 명령은 macOS·Linux
어디서나 같은 형식을 낸다 — 괄호 안은 epoch 초다.

```bash
TZ=Asia/Seoul date '+%Y-%m-%d %H:%M:%S %Z (%s)'
```

- **시작일시**는 아래 0번에서 남긴 값을 옮겨 적는다. 찾을 수 없으면(세션이 바뀌었거나 대화가
  요약되어 사라졌으면) 짐작하지 말고 `알 수 없음`과 사유를 적는다.
- **종료일시**는 이 블록을 출력하는 그 턴에서 명령을 실행해 얻는다. 추적·뒷정리가 남아
  있어도 이 블록을 출력한 시각이 기준이다.
- **걸린시간**은 두 epoch 값의 차이를 셸로 계산한다(`echo $(( 종료 - 시작 ))`를 시·분으로
  옮긴다). 머리로 계산하지 않는다. 시작일시가 `알 수 없음`이면 걸린시간도 `알 수 없음`이다.

### 시작할 때

0. **작업 지시를 받은 첫 턴에 위 명령으로 시작일시를 얻어 그 턴의 응답에 적는다.** 응답에
   남겨야 마지막 블록에서 다시 가져다 쓸 수 있다.
1. `.ai/status.md`의 우선순위와 `.ai/issues/`를 읽고, 할 일이 범위 안인지 확인한다(AGENTS.md 2절).
   **[`.ai/work-result/`](./work-result/)의 가장 최근 문서 한두 개도 함께 읽는다.**
   이어지는 작업이 아니어도 읽는다 — 앞선 세션이 무엇을 건드렸고 무엇을 남겨 두었는지를
   `status.md`의 한 줄은 말해 주지 않는다. **인덱스 표 맨 위 한두 줄만 본다** —
   폴더 전체를 훑지 않는다. 비어 있으면 건너뛴다.
   **계획 문서를 세운 작업이면 착수 전에 그 계획을 `Approved`로 바꾼다** — 소유자 승인이
   필요한 계획은 승인을 받은 뒤에. `Draft`인 계획은 실행하지 않는다(`.ai/plan/`).
2. **이전에 연 PR이 아직 열려 있으면 상태와 기존 추적을 확인한다.** 세션 종료만으로 예약이
   사라졌다고 가정하지 않는다. 아래 6번의 순서로 기존 예약을 재사용하고, 없는 경우에만 만든다.

### PR을 열 때

3. **코드 리뷰를 한 번 돌리고 지적을 반영한다**(8절). 문서 전용 작업은 해당 없다.
4. **문서 검사 셋과 완료 조건을 로컬에서 통과시킨다**(AGENTS.md 9절).
5. **작업한 변경만으로 PR을 열고, 받은 링크를 채운 결과 문서를 `.ai/work-result/`에 만들어
   같은 브랜치에 커밋한다**(8절). 결과 문서를 PR보다 먼저 커밋하지 않는다 — 링크가 없어
   임시값을 적게 되고, 그 값이 CI와 리뷰 도구에 매번 걸린다. **PR을 연 뒤 첫 push가 결과
   문서다** — 일반 PR은 opened부터 문서가 없으면 실패하고 Draft만 경고한다. 문서를 추가하면
   검사가 통과한다. 원본 템플릿 저장소의 기록 예외는 루트 README가 정한다. **계획 문서가 있으면 결과
   문서 본문에서 그 계획을 링크한다** — 머리말 필드를 새로 두지 않고, 끝났다고 계획의 상태를
   바꾸지 않는다. 남은 단계는 `.ai/status.md`의 「진행 중」 표에 계획의 단계 번호로 적는다.
6. **PR을 연 턴에 사용 가능한 추적 기능과 기존 예약을 확인한다.** 도구별 파일이 기능별
   수명과 지원 조건을 정한다. 다음 순서를 지킨다.
   - **기능 확인 → 대상 PR의 기존 구독·예약 조회 → 재사용 또는 생성** 순서다. 동일 저장소·PR·
     목적의 활성 예약을 중복 생성하지 않는다. 기존 예약을 조회할 수 없으면 생성하지 않는다.
   - 예약 ID·대상 저장소/PR·실행 환경·주기·만료/종료 조건을 PR 본문의 추적 항목에 남긴다.
     영속 예약과 세션 예약을 구분하고, 추적 수단이 실제 생성된 결과를 확인한다.
   - 생성 오류는 원인을 확인하고 제한적으로 재시도한다. 기능이 없거나 조회·생성이 실패하면
     PR 본문과 응답에 한계를 기록하고, 다음 작업 턴에 상태를 직접 확인한다. 실행 수단 없이
     백그라운드 추적을 약속하지 않는다.

### 추적할 때 — PR이 열려 있는 동안

7. **머지/close 여부 → CI 상태 → 리뷰 코멘트 → 소유자의 이모지 신호**(8절) 순으로 확인한다.
   이모지는 **코멘트 두 자리를 본다** — 코멘트에 달린 반응과 소유자가 쓴 코멘트 본문(8절).
8. 리뷰 지적 반영·수정 범위 재검증·CI 수리를 수행한다. 8절의 승인자·대상 SHA·최신 검사
   조건을 모두 충족하면 머지하고, 확인된 중단 지시가 있으면 close한다.
9. **PR이 열려 있으면 기존 추적이 유효한지 확인한다.** 반복 예약이 살아 있으면 유지한다.
   일회 예약이 끝났거나 만료됐으면 6번의 조회를 거쳐 다음 확인을 설정한다. 기능이 없으면
   직접 확인으로 전환했다고 알린다. 변화가 없다는 이유로 중복 예약을 만들지 않는다.

### 끝낼 때 — 머지되었거나 close되었을 때

10. **그 턴 안에서 뒷정리를 끝낸다. 소유자가 말하지 않아도 한다.**
    - **걸어 둔 추적을 전부 해제한다** — 구독·예약 어느 것도 남기지 않는다.
    - **이번 작업에 쓴 브랜치를 지운다** — 머지됐으면 로컬·원격 모두, close됐으면 로컬만.
      남기거나 지우지 못한 브랜치는 이름을 알린다(예외와 사유는 8절).
    - `.ai/status.md`와 작업 결과 문서가 최종 상태를 반영하는지 확인한다(AGENTS.md 9절).
    - **남은 지적·미해결은 `.ai/issues/`에 등재한다.** close된 PR의 지적도 사라지지 않는다.
11. **머지·close·소유자의 중지 지시가 있으면 해당 PR의 추적을 해제한다.** 예약 만료·권한
    상실·실행 환경 종료로 자동 추적을 계속할 수 없으면 그 한계와 다음 확인 방법을 알린다.
    중지한 것과 환경 때문에 실행되지 않는 것을 구분한다.
