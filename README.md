# AI 프로젝트 기본 템플릿

새 프로젝트를 시작할 때 그대로 가져다 쓰는 **AI Pair 개발용 문서 세트**다. 실제 프로젝트를
운영하며 정리한 규칙을 프로젝트 독립적으로 일반화했다. GitHub 템플릿 저장소이므로 **Use this
template** 버튼으로 바로 새 저장소를 만들 수 있다.

**어느 도구로 읽든 같은 규칙을 읽게** 하는 것이 이 세트의 목적이다. 공통 규칙의
단일 출처(single source of truth)를 `AGENTS.md` 하나로 두고, 도구별 파일은 그것을 가리키기만
한다. Codex는 `AGENTS.md`를 직접 읽고, Claude Code는 `AGENTS.md`를 가리키는 얇은 `CLAUDE.md`를
읽는다. 에이전트를 하나만 쓰든 여럿을 쓰든 구조는 같다.

**`AGENTS.md`에는 프로젝트와 무관한 고정 규칙만 둔다.** 코드 배치·빌드 명령·아키텍처 원칙·
코딩 가이드·검증 방법처럼 프로젝트마다 갈리는 것은 전부 `.ai/project-rules.md`가 담는다.
그래서 `AGENTS.md`는 프로젝트가 고치지 않고, 템플릿이 갱신되면 **통째로 바꿔 받을 수 있다.**

특정 언어·프레임워크·프로토콜을 전제하지 않는다 — 결정할 값은 전부 `{{...}}` 자리표시자로
비워 두었고, 실제 프로젝트가 채운다.

이 저장소 자체는 **템플릿을 관리하는 곳**이라 자기 작업 기록(작업 결과·이슈·ADR)을 남기지
않는다. `.ai/`의 폴더와 인덱스는 비어 있는 상태로 배포되며, 가져다 쓸 프로젝트가 채운다.

> **템플릿을 손보는 작업에만 해당하는 예외다.** `AGENTS.md` 8·9절은 작업이 끝나면
> `.ai/work-result/`에 결과를 남기고 `.ai/status.md`를 갱신하라고 정하는데, 이 저장소에는
> 그 규칙을 적용하지 않는다 — 남겨 봐야 템플릿을 가져다 쓰는 쪽에는 남의 기록이기 때문이다.
> 이 README는 도입 시 삭제되므로 예외도 함께 사라진다. **가져다 쓴 프로젝트에서는 8·9절을
> 그대로 지킨다.**

## 구성

```text
ai-project-template/
├── README.md                          # (이 파일) 템플릿 사용법
├── AGENTS.md                          # 공통 고정 규칙 단일 출처 (그대로 쓴다)
├── CLAUDE.md                          # Claude Code 전용 안내 (AGENTS.md를 가리킴)
├── .gitignore                         # 공통 무시 규칙 (언어별 규칙은 도입 시 추가)
├── .github/
│   ├── pull_request_template.md       # PR 본문 템플릿
│   ├── workflow-template.yml          # Actions 워크플로 템플릿 (분 절약 가드레일 포함)
│   ├── file-size.json                 # 파일 줄 수 상한·예외·baseline
│   ├── scripts/
│   │   ├── check_markdown_links.py    # 문서 내 상대 링크 깨짐 검사
│   │   ├── check_doc_index.py         # .ai/ 인덱스·머리말 규약 검사
│   │   ├── pr_field.py                # └ 그 검사가 쓰는 `PR` 필드 규칙 모듈
│   │   └── check_file_size.py         # 파일 줄 수 상한 검사 (래칫)
│   └── workflows/
│       └── checks.yml                 # 위 검사들을 PR·main push마다 실행
└── .ai/                               # AI 에이전트 공용 작업 메모리 (개발용)
    ├── README.md                      # .ai 폴더 규약 (문서별 역할, 추가법, 상태 어휘)
    ├── project-rules.md               # 이 프로젝트만의 규칙 ★ AGENTS.md가 위임한 자리
    ├── backlog.md                     # 만들고 싶은 것 (아직 범위 아님)
    ├── status.md                      # 구현 현황 (상태의 단일 출처)
    ├── design/
    │   ├── README.md                  # 설계 문서 인덱스 표
    │   └── 0000-template.md           # 설계 문서 템플릿 (덮어쓰는 문서)
    ├── adr/
    │   ├── README.md                  # ADR 인덱스 표
    │   └── 0000-template.md           # 결정 기록 템플릿
    ├── issues/
    │   ├── README.md                  # 오픈 이슈 인덱스 표
    │   └── 0000-template.md           # 이슈 템플릿
    └── work-result/
        ├── README.md                  # 작업 결과 문서 인덱스 표
        └── 0000-template.md           # 작업 결과 문서 템플릿
```

`.ai/`는 저장소에 함께 커밋되지만 **배포물이 아니라 개발용 문서**다 — 저장소에서만 읽고,
사용자용 문서(제품 README, 공개 가이드)와 섞지 않는다.

각 문서의 역할과 갱신 방식은 [`.ai/README.md`](./.ai/README.md)가 정한다. 요약하면
**공통 규칙은 `AGENTS.md` 하나**, **프로젝트 규칙은 `.ai/project-rules.md` 하나**,
**범위와 진행은 `.ai/status.md` 하나**, 나머지는 그 셋을 뒷받침한다.

`.ai/design/`은 **미리 만들지 않는다** — 컴포넌트가 실제로 생겨 구조를 설명해야 할 때 파일을
추가한다. 인터페이스 계약 등 그 밖의 문서도 필요해질 때 `.ai/` 아래에 두고 `.ai/README.md`에
등록한다.

## 적용 방법

쓰는 순서는 둘로 나뉜다.

1. **사람이 저장소를 가져온다** (1단계). 이때 딸려 오는 규칙은 **프로젝트와 무관해 이미
   완성된 문장**이라 손댈 것이 없다.
2. **AI가 프로젝트의 지침과 정보를 채운다** (2단계 이후). `.ai/project-rules.md`와 `{{...}}`
   자리가 그 대상이다. **`AGENTS.md`는 채울 것이 없다** — 전부 완성된 고정 규칙이다.

그래서 이 템플릿은 **바뀌지 않는 것만 문장으로 확정하고, 나머지는 자리만 남긴다.** 형식을
강제하지 않으니 프로젝트에 맞게 쓰면 된다.

> **순서 주의.** 이 README는 마지막 단계에서 지운다 — 위아래 안내가 여기 있기 때문이다.

1. **가져오기.** 두 방법 중 하나를 고른다. 어느 쪽이든 **템플릿의 커밋 히스토리는 딸려오지
   않는다.**

   ### 방법 A — GitHub 웹 (권장)

   원격 저장소가 바로 만들어지고 연결까지 끝난다.

   1. 브라우저에서 <https://github.com/ChoccoJang/ai-project-template> 를 연다.
   2. 오른쪽 위 초록색 **`Use this template`** 버튼 → **`Create a new repository`** 를 고른다.
   3. 새 저장소 이름과 공개 범위(Public/Private)를 정하고 **`Create repository`** 를 누른다.
   4. 만들어진 저장소를 로컬로 내려받는다.

      ```bash
      git clone https://github.com/<내계정>/<새저장소>
      cd <새저장소>
      ```

   ### 방법 B — 명령줄만으로

   GitHub를 쓰지 않거나 원격 저장소를 아직 만들지 않았을 때. 내려받아 `.git`을 지우고 새로
   시작한다.

   **macOS · Linux**

   ```bash
   git clone --depth 1 https://github.com/ChoccoJang/ai-project-template <새프로젝트>
   cd <새프로젝트>
   rm -rf .git
   git init && git add -A && git commit -m "chore: 문서 세트 도입"
   ```

   **Windows (PowerShell)**

   ```powershell
   git clone --depth 1 https://github.com/ChoccoJang/ai-project-template <새프로젝트>
   Set-Location <새프로젝트>
   Remove-Item .git -Recurse -Force
   git init; git add -A; git commit -m "chore: 문서 세트 도입"
   ```

   **특정 버전으로 고정하려면** `--branch <태그>`를 붙인다 — 태그 목록은
   [Releases](https://github.com/ChoccoJang/ai-project-template/releases)에 있다. 붙이지
   않으면 기본 브랜치의 최신 상태를 받는다(방법 A의 `Use this template`도 늘 최신이다).

   원격을 나중에 붙이려면 저장소를 만든 뒤 연결한다.

   ```bash
   git remote add origin <새-원격-URL>
   git push -u origin main
   ```

   > 원격 없이 쓸 수도 있다. 그때는 `AGENTS.md` 8절의 PR 규칙이 "해당 없음"이 되고, 기본
   > 브랜치에 직접 커밋한다.

2. **자리표시자를 채운다.** `{{...}}`는 **그 자리에서 채우는 것**이지 일괄 치환 대상이
   아니다. 문서를 쓸 때마다 그 자리에 내용을 넣는다.

   예외는 하나, **`.ai/project-rules.md` 4절의 빌드/실행 표**다. 저장소 전체에서 같은 값이고
   에이전트가 가장 먼저 찾는 정보이니 도입 시점에 채운다.

   | 자리표시자 | 의미 | 예시 |
   |---|---|---|
   | `{{설치-명령}}` · `{{빌드-명령}}` · `{{테스트-명령}}` · `{{실행-명령}}` · `{{린트-명령}}` | `.ai/project-rules.md` 4절 빌드/실행 표 | `npm ci`, `npm run build`, `npm test` |

   나머지(`{{아키텍처 불변 원칙…}}`, `{{무엇을 만드는가}}`, `{{하고 싶은 것}}` 등)는 해당
   문서를 쓸 때 채운다. 템플릿 파일(`0000-*`)에는 그대로 둔다.

3. **`.ai/project-rules.md`를 채운다.** 이 문서의 절 번호는 `AGENTS.md`와 맞춰져 있다 —
   `AGENTS.md` 4절이 위임한 것은 여기 4절에 있다. **어느 절의 어느 부분을 이 문서가 채우는지는
   `AGENTS.md` 앞머리의 절 목록 표가 알려준다.**

   - **형식을 강제하지 않는다.** 필요한 만큼만 쓰고, 해당 없으면 "해당 없음" 한 줄로 둔다.
     **절 자체를 지우지는 않는다.**
   - **3·4절(코드 배치 / 빌드·실행)만 채워도 에이전트가 일할 수 있다.** 나머지는 프로젝트가
     자라면서 채운다.
   - **분량이 늘면 이 문서에 쌓지 말고** 개발 가이드·코딩 표준 문서를 따로 두고 6절에서
     가리킨다. 규칙 문서가 프로젝트와 함께 부풀지 않게 하는 것이 이 분리의 목적이다.

   **`AGENTS.md`는 손대지 않는다.** 고칠 이유가 생기면 그 자체가 결정이므로 소유자가 정하고
   ADR로 남긴다. 이 프로젝트가 무엇인지는 프로젝트 `README.md`에, 무엇을 만들기로 했는지
   (범위)는 `.ai/status.md`의 구현 현황 표에 적는다.

4. **절 번호는 바꾸지 않는다.** 새 규칙이 필요하면 다음 번호로 이어 붙인다. 다른 문서·커밋이
   "AGENTS N절"로 참조하는 관례상 이미 매긴 번호는 바꾸지 않고, 빈 번호를 미리 예약하지도
   않는다.

5. **에이전트별 파일.** Codex는 별도 파일이 필요 없다 — `AGENTS.md`를 직접 읽는다.
   Claude Code는 `CLAUDE.md`를 그대로 둔다. 그 외 도구를 추가한다면 같은 형태로
   (공통 규칙은 중복하지 않고 `AGENTS.md`를 가리키는 얇은 파일) 만든다.

6. **마무리.**
   - **가져온 템플릿 버전을 남긴다** — 도입 커밋 메시지나 도입 작업의 결과 문서에
     `ai-project-template v1.0.0`처럼 적는다. 이 README는 아래에서 지우므로, 적어 두지
     않으면 어느 버전에서 왔는지 알 수 없다.
   - `.ai/project-rules.md`의 안내용 HTML 주석을 값으로 바꾼다.
   - `.ai/backlog.md`와 `.ai/status.md`의 `{{...}}` 예시 행을 지우고 실제 계획을 적는다.
     (`.ai/`의 인덱스는 비어 있는 상태로 배포되므로 지울 기록은 없다.)
   - `LICENSE` 파일을 프로젝트에 맞게 추가한다(이 템플릿은 라이선스를 정해 두지 않는다).
   - `.gitignore`에 언어/도구별 규칙을 추가한다.
   - 이 `README.md`를 지우고 프로젝트 README로 대체한다.

     ```bash
     rm README.md
     ```

     ```powershell
     Remove-Item README.md
     ```

## 검사

`.github/workflows/checks.yml`이 **PR과 기본 브랜치 push마다** 세 가지를 검사한다.
새 워크플로를 늘리지 않고 한 job의 step으로 더한 형태다(AGENTS 9절).

| 스크립트 | 무엇을 막는가 |
|---|---|
| `check_markdown_links.py` | 인덱스·문서의 상대 링크가 **없는 파일**을 가리키는 실수 |
| `check_doc_index.py`<br>(+`pr_field.py`) | 파일을 만들고 **인덱스에 등록하지 않은** 실수, 한글 파일명, 번호 중복, `Phase`·`PR`·`갱신일` 필드 누락·공백, 상태 어휘 오타, 인덱스 표와 파일 머리말의 상태 불일치, **없는 절을 가리키는 "N절" 참조**, 그리고 작업 결과 문서 **`PR` 필드의 값**(아래 표) |
| `check_file_size.py` | 파일이 줄 수 상한(기본 400)을 넘는 것. **이미 넘던 파일은 더 늘어날 때만** 잡는다. 진입 문서 3개는 **합계 예산**, `project-rules.md`·`status.md`는 자체 상한으로 본다 |

### 작업 결과 문서의 `PR` 필드

`check_doc_index.py`는 이 필드만은 값까지 본다. 규칙의 **뜻**은
[`.ai/work-result/README.md`](./.ai/work-result/README.md)가 정하고, 여기서는 어느 실행에서
무엇이 걸리는지만 적는다.

| 값 | 로컬 (옵션 없음) | 기본 브랜치 push | PR 실행 |
|---|---|---|---|
| PR 링크 — `[#12](https://.../pull/12)` | 통과 | 통과 | 통과 |
| `없음(사유)` | 통과 | 통과 | **이 PR이 새로 추가한 문서면 실패** |
| `없음(직접 push, abc1234)` | 통과 | 통과 | 통과 — 그 커밋이 **이 PR 전에 이미 있던 것**이어야 한다 |
| `미정` | 통과 (경고를 찍는다) | **실패** | **실패** |
| `#12` · 사유 없는 `없음` · `해당 없음` · 채우지 않은 자리표시자 | 실패 | 실패 | 실패 |

CI가 켜는 옵션은 셋이다.

| 옵션 | 무엇 |
|---|---|
| `--merge-gate` | `PR: 미정`을 실패로 본다 |
| `--added "경로들"` | 이 PR이 **새로 추가한** 문서 목록. 그 문서의 `없음(...)`을 실패로 본다 |
| `--base 커밋` | 뒤늦은 기록이 가리키는 커밋이 **그 전에 이미 있던 것**인지 본다 |

`--added`와 `--base`는 워크플로가 머지 커밋의 첫 부모(base)와 비교해 계산한다. 그래서
`checks.yml`의 `fetch-depth: 0`이 함께 가야 한다 — 줄이면 뒤늦은 기록의 커밋을 확인하지
못하고 경고만 남긴다.

### 필요한 것 — Python 3.11 이상

세 검사는 **파이썬 표준 라이브러리만** 쓴다. 설치할 패키지는 없고 인터프리터만 있으면 된다.

```bash
python3 --version        # Python 3.11.x 이상이면 준비 끝
```

없다면 설치한다. GitHub Actions 러너(`ubuntu-latest`)에는 이미 들어 있어 CI는 손댈 것이 없다.

| 환경 | 설치 |
|---|---|
| macOS | `brew install python` (또는 [python.org](https://www.python.org/downloads/) 설치본) |
| Ubuntu · Debian | `sudo apt install python3` |
| Windows | [python.org](https://www.python.org/downloads/) 설치본. 설치 화면의 **Add python.exe to PATH**를 켠다. PowerShell에서는 `python3` 대신 `python`일 수 있다 |

3.11 미만에서는 `X | None` 타입 표기 때문에 실행되지 않는다.

### 돌리기

CI에 올리기 전에 로컬에서 먼저 돌린다.

```bash
python3 .github/scripts/check_markdown_links.py
python3 .github/scripts/check_doc_index.py
python3 .github/scripts/check_file_size.py
```

**로컬에서는 옵션 없이 돌린다.** 작업 중에는 아직 PR이 없어 `PR: 미정`이 정상이기 때문이다
(위 `PR` 필드 표). 대신 `미정`을 보면 **경고를 찍으므로**, 로컬 초록을 "다 됐다"로 오해할
일은 없다. 머지 직전 상태를 그대로 보려면 `--merge-gate`를 붙인다.

`check_doc_index.py`는 같은 폴더의 `pr_field.py`를 import한다 — **다른 저장소로 옮길 때 두
파일을 함께** 복사한다.

크기 기준은 대상마다 다르고 `.github/file-size.json`이 정한다.

| 대상 | 기준 |
|---|---|
| 코드·그 밖의 파일 | 400줄. **이미 넘던 파일은 `baseline`에 적어 두고 더 늘어날 때만** 실패한다(래칫). 소급 적용해 한꺼번에 쪼개게 만들면 줄 수만 맞춘 기계적 분할이 나온다 |
| 진입 문서 `AGENTS.md`·`CLAUDE.md`·`.ai/README.md` | 파일별 상한 없이 **합계 예산**. 한쪽에서 밀어내 다른 쪽에 넣으면 고정 비용이 그대로다 |
| `.ai/project-rules.md` · `.ai/status.md` | 자체 상한. 프로젝트·범위와 함께 자라므로 고정 비용이 아니다 |
| 인덱스 표·백로그 | 상한 없음. 항목이 쌓이는 것이 정상이다 |
| 개별 기록 (ADR·이슈·작업 결과·설계) | 300줄. 넘으면 한 파일에 여러 건이 섞인 것이다 |

줄어들면 `--update-baseline`으로 기준선을 낮춘다.

## 설계 의도 (왜 이렇게 나눴나)

- **규칙은 한 곳에, 규칙만.** 도구별 파일에 규칙을 복사하면 반드시 갈라지므로 공통 규칙은
  `AGENTS.md`에만 둔다. 그리고 거기에는 **지켜야 할 것만** 둔다 — 프로젝트 소개·범위·설계·
  배경은 규칙이 아니고, 규칙보다 훨씬 자주 바뀌어 규칙 문서를 흔든다. 배경은 ADR, 절차는
  `.ai/README.md`, 예시는 템플릿 파일이 갖는다.
- **고정 규칙과 프로젝트 규칙을 파일로 가른다.** 한 파일에 두면 프로젝트가 자랄 때마다 규칙
  문서가 함께 부풀고, 템플릿이 갱신돼도 통째로 받을 수가 없다 — 어디까지가 내 프로젝트 것인지
  구분되지 않기 때문이다. `AGENTS.md`는 손대지 않는 고정 규칙, `.ai/project-rules.md`는
  프로젝트가 채우는 자리, 그보다 길어지는 개발 가이드는 또 그 바깥에 둔다.
- **절차는 순서 있는 체크리스트로 둔다**(`AGENTS.md` 10절). 절차가 산문에 흩어져 있으면
  도구마다 빠뜨리는 단계가 달라진다 — 특히 PR을 연 뒤의 추적과 머지·close 뒤의 뒷정리가
  조용히 빠진다. 그래서 순서를 한 곳에 모으고, **마지막 응답에 체크리스트를 옮겨 적어 각
  항목에 답하게** 한다. 도구별 파일은 그 절차를 무슨 기능으로 수행하는지(수단)만 정한다.
- **머지도 close도 소유자의 코멘트 이모지 하나로 지시한다**(`AGENTS.md` 8절). 🚀는 머지,
  👎(코멘트 본문에서는 ❌·🛑도)는 중단이다. **읽는 자리를 코멘트로 한정한** 것은 볼 곳이
  여럿이면 결국 한 곳을 놓치기 때문이다. 신호가 없으면 어느 쪽도 하지 않고, 신호가 오면 그
  턴 안에서 뒷정리까지 끝낸다 — 매번 채팅으로 "이제 닫아라"라고 말하지 않아도 되게 하는 것이
  목적이다.
- **범위와 진행은 한 표에서.** "무엇을 만들기로 했나"와 "어디까지 됐나"는 같은 항목의 두
  얼굴이다. 나눠 적으면 한쪽만 갱신된다.
- **갱신 방식이 다른 문서를 섞지 않는다.** 덮어쓰는 문서(백로그·상태·설계)와 추가만 하는
  문서(ADR·작업 결과)를 한 파일에 두면, 최신 상태를 보려면 과거를 걷어내야 하고 과거를
  보려면 이미 덮어쓴 뒤다.
- **현재 설계와 그 근거를 가른다.** 지금 모습은 `.ai/design/`에 덮어쓰고, 왜 그렇게 됐는지는
  ADR에 쌓는다. 진화하는 설계를 불변 기록에만 두면 현재 모습을 알기 위해 ADR을 시간순으로
  읽어 합성해야 한다.
- **같은 글을 두 번 쓰지 않는다.** PR 본문과 작업 결과 문서는 담을 것을 나눠 갖는다.
  사본을 두면 반드시 한쪽이 낡는다.
- **규약은 CI가 지킨다.** 인덱스 등록·파일명·머리말 형식·파일 크기는 사람의 성실성이 아니라
  스크립트가 확인한다. 검사되지 않는 규약은 결국 지켜지지 않는다.
- **AI에게는 크기 압력이 없다.** 사람은 긴 파일을 스크롤하다 지쳐서 나누지만 에이전트는
  지치지 않고, 기존 파일에 덧붙이는 쪽이 늘 더 안전하다. 그래서 파일 크기만은 규칙과 검사로
  바깥에서 눌러 준다 — 대신 상한에 맞춰 자르지 말라는 원칙을 함께 둔다.
- **문서는 최소로 시작한다.** 설계 문서와 인터페이스 계약은 미리 만들지 않고, 그것을 말로
  설명해야 하는 순간에 만든다.
